# Architecture

Projects are persisted in a separate SQLite table and scoped to a workspace. A Session's optional `projectId` is validated against the same workspace; archived projects retain their existing Sessions and files. Local directory selection uses a native picker and validates existing folders. Projects independently retain a local-location flag, associated server profile IDs, an optional local directory, and an optional Linux remote directory; locations are not mutually exclusive project categories. Remote directories are never resolved as local folders. Each Session defaults to Local and may select one associated server; task/approval/terminal entry points verify project membership. Local PTY and CLI launches use the stored local directory even when the selected task target is a server; CLI execution remains local. Remote project paths supply the initial SFTP browsing location. Engine scopes incorporate project identity and directory alongside target/model, preserving old native/API contexts when a Session is moved. Renaming a project does not change its engine scope. Project metadata does not grant remote-command permission or automatically expose file contents to model requests.

```text
React renderer
    │ typed, explicitly enumerated IPC through a sandboxed preload
Electron main process
    ├── Store → SQL.js SQLite → atomic database replacement
    │             └── OS safeStorage encryption for secrets
    ├── SSHService → ssh2 shell / exec / SFTP
    ├── LocalTerminals → node-pty
    ├── Approvals → target-bound, expiring, single-use command tickets
    └── AgentService → model HTTP API / local CLI JSONL subprocess
```

The renderer cannot access Node.js, credentials, or arbitrary IPC channels. Main-process handlers validate payloads and verify the calling window/frame. New windows and navigations are denied. The renderer uses a content security policy and renders model output as plain text, not HTML.

Remote command execution is separate from the interactive SSH terminal. The renderer first registers a proposal; the main process snapshots its exact server ID, command and Session permissions. Execution consumes the ticket and presents a native confirmation dialog unless Bypass permissions was explicitly selected. Read-only is rejected; target, directory and permissions are rechecked before SSH `exec`. Bypass skips the command dialog and records `approval: bypassed`; SSH host trust remains required. Changing or disconnecting a server revokes pending tickets. Commands are serialized per server and are never retried automatically.

Host verification uses SHA-256 of the server's public key. A newly accepted fingerprint is persisted only after authentication succeeds. Existing fingerprints must match exactly. Changing the target host or port clears its pin and stored credential.

Terminal output is batched every 24 ms with a bounded pending buffer, a bounded renderer replay buffer, and a 5,000-line xterm scrollback. This alpha drops excess display output instead of attempting complete logging. Commands retain up to approximately 1 MiB of decoded text; excess output is marked as truncated.

Workspace metadata and layout preferences are schema-validated and stored in the renderer's local storage (`axonssh.workspaces.v1`); they contain server and active-Session IDs, not credentials. Existing profiles are associated with the original workspace when upgrading. Server credentials and connection settings remain in the main-process database, and the same profile can be associated with multiple workspaces. Sessions persist their titles, target, engine, and messages in SQLite. Assistant turns are persisted as running before execution and completed/error afterwards; unfinished turns become interrupted when reopening the database. Execution approvals bind the Session ID and proposal key along with the server and command, and resulting activity/output records belong to that Session. Legacy activity is retained in a historical Session. Drafts and running tasks are scoped to a Session in memory, while terminal tabs remain workspace-level. Panel placement uses CSS grid: terminal components stay mounted across layout changes, panel collapse, activity navigation, and workspace/Session switches. Application restarts restore the layout and conversations, but not live terminals.

SQLite runs in the main process through SQL.js to avoid another native addon. Writes export to a private temporary file and atomically replace the database. This is appropriate for the alpha's small profile/history dataset; a native SQLite service and dedicated I/O worker should replace it if write volume grows. Main-process SSH and PTY orchestration should likewise move to dedicated workers before scaling to many simultaneous sessions.

The built-in assistant is advisory: it returns text and suggested commands. There is no autonomous tool loop or implicit terminal-context collection. External CLI adapters likewise do not receive a remote execution bridge. Interactive CLI terminals receive the selected Session permission flags. Native local tools do not enter the application remote audit channel.

Provider requests have cancellation and a three-minute deadline. External subprocess output is bounded. CLI protocol compatibility is intentionally isolated in `AgentService`, so a later official SDK/app-server adapter can replace it without changing the server, approval, or terminal layers.

Native CLI continuity is keyed by engine, target identity, and model choice. Session records persist native IDs, acknowledged message cursors, delivered operation IDs, and handoff attempts. CLI stdout supplies Codex `thread.started.thread_id` or Claude `session_id`; resume always uses that exact ID, never the most recent global session. Prompts are sent through stdin. A successful turn advances the cursor; failures preserve audit data and require explicit recovery, while interrupted pending states are normalized on database reopen. Handoff payloads contain bounded excerpts and command-status metadata, never implicit raw command outputs or inherited approval tokens. No extra model call generates the packet. Provider usage metadata is retained as reported, without treating it as a bill or a cache guarantee.

The built-in DeepSeek adapter uses the OpenAI-compatible `/chat/completions` endpoint with `thinking`, `reasoning_effort`, JSON output, and an 8,192-token output cap. Its API message chain is stored independently per target/model/endpoint/protocol and appended rather than reserialized from the UI transcript. CLI-to-API and API-to-CLI switches use the same handoff cursor and operation provenance. API context is limited to 96,000 characters; exceeding this limit requires an explicit re-establishment that retains old records. The adapter does not migrate hidden reasoning or auto-execute tool calls. Its cache metrics come from API usage metadata, not a cost estimate.

Session permission policy is persisted and enforced in the main process; legacy operation modes are ignored. New Sessions always start locally, even in server-associated projects, and switching the target is explicit. Local tasks collect OS metrics; connected server tasks use fixed-path read-only SFTP reads (`/etc/os-release`, `/proc/loadavg`, `/proc/meminfo`, `/proc/uptime`, at most 4 KiB each). Native CLI local tools follow the selected policy; server-target chat restricts local tools and returns application SSH command cards. Local application commands use a bounded hidden shell subprocess in the project directory or home, with a 60-second timeout and 1 MiB output cap. Read-only blocks application commands. Ask/accept-edits require native confirmation; Bypass skips the dialog. Session target, directory and permissions are checked before execution, and switching them is blocked during active tasks or commands. SSH connection events update UI status independently of terminal tabs. No autonomous remote tool loop or native CLI approval bridge is provided.
